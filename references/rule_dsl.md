# 规则识别与人工审核（所有模型必须遵守）

规则都是用户自定义的中文文本，数据库只负责存。每段规则文本叫一个**条款**，本批次（一个年度）的条款来自两处：

| 来源 | 位置 | 生效范围 |
|---|---|---|
| 通用规则 | 规则表的「规则内容」 | 本年度全部期次 |
| 计划·参培对象 | 计划表的「参培对象」 | 只对该期次 |
| 计划·调训规则 | 计划表的「调训规则」 | 只对该期次 |

**模型的工作只有一件：把条款原文翻译成下面这种受限 JSON。**翻译结果必须经用户在审核表里确认才会生效，
确认后锁定；之后不论哪个模型运行都用这份已确认的条件，名单逐行一致。

## 一、固定流程（不得跳步）

只用一条命令驱动，**它打印什么就做什么**：

```bash
node index.js 名单 --年度 2027
```

| 退出码 | 含义 | 谁做 | 做什么 |
|---|---|---|---|
| 2 | 有条款待翻译或被驳回 | 模型 | 打开 `输出/规则解析/待翻译规则.json`，按本文逐条填「分支」「未译部分」（驳回的看「驳回意见」）→ `node index.js 规则 登记` → 再跑 `名单` |
| 3 | 有条款待审核 | 用户 | 把审核表路径告诉用户，等用户审完 → `node index.js 规则 确认 "<审核表>"` → 再跑 `名单` |
| 0 | 名单已生成 | — | 把文件位置和四个指纹告诉用户 |

`规则 登记` 报错时按报错逐条改草稿再登记，一条不合格就全部不登记。

状态：**待翻译 → 待审核 → 已确认**；驳回回到待翻译；原文改一个字指纹就变，回到待翻译。
已确认的条款下次不用再审，只有新增、改过、被驳回的条款需要处理。

**禁止**：替用户在审核表里填审核结果；自己写脚本算名单；改 `scripts/` 下的文件；手改 `规则译文库.json`；
用 `--覆盖` 重译已确认的条款（除非用户明确要求）。

## 二、译文格式

```json
{
  "指纹": "照抄草稿",
  "依据": ["从原文原样摘出的片段"],
  "分支": [
    { "动作": "准入", "当": <条件>, "理由": "不满足时的剔除理由" },
    { "动作": "剔除", "当": <条件>, "理由": "剔除理由" },
    { "动作": "加分", "当": <条件>, "分": 20, "理由": "加分理由" }
  ],
  "未译部分": [ { "原文": "原文片段", "原因": "为什么不能变成筛选条件" } ]
}
```

| 动作 | 含义 |
|---|---|
| 准入 | 必须满足，不满足就剔除（参培对象多用这个） |
| 剔除 | 满足就剔除（“不含……”“不安排……”“不重复”） |
| 加分 | 满足就加分；同一条款自上而下取**第一个**命中的加分分支（分档写法：高档在前） |

| 规定 | 内容 |
|---|---|
| 通用规则的动作 | 硬规则只能用 准入 / 剔除；软规则只能用 加分 |
| 计划条款的动作 | 三种都能用，按句意选 |
| 分 | -100~100 的非零整数 |
| 理由 | 80 字以内；剔除必填；可用占位符显示实际值，如 `{人员.年龄}`、`{AB角冲突}` |
| 依据 / 未译部分.原文 | 必须是原文里**原样**出现的片段 |
| 未译部分 | 原文中无法用字段与指标表达的句子必须列在这里并写原因，**不得编字段、不得近似硬凑**；分支为空时必须有未译部分 |

不允许出现表里以外的键（草稿里的 来源、名称、原文、适用期次、驳回意见、原译文 可以保留，登记时自动去掉）。

## 三、条件写法（与审核表一一对应）

条件只有一种形状：**"总是"，或者若干「或组」，每个或组是若干「条件行」**。
组内的条件行是“且”，组与组之间是“或”。

```json
"当": "总是"
"当": [[ 条件行 ]]                                  // 一个条件
"当": [[ 条件行A, 条件行B ]]                        // A 且 B
"当": [[ 条件行A ], [ 条件行B ]]                    // A 或 B
"当": [[ A, B ], [ C ]]                             // (A 且 B) 或 C
```

条件行：

```json
{ "字段": "人员.年龄", "运算": ">=", "值": 55 }
{ "指标": "参培次数", "参数": { "范围": "指定年度", "年度": 2026, "班次": "同班次" }, "运算": ">=", "值": 1 }
```

“不是/不含”用反向运算表达：`!=`、`不包含`、`不属于`、`为空`，或者把动作从准入改成剔除。

### 字段

| 字段 | 类型 | 字段 | 类型 |
|---|---|---|---|
| 人员.单位 | 文本 | 计划.班次名称 | 文本 |
| 人员.地区 | 文本 | 计划.期次 | 文本（如「第五期」） |
| 人员.姓名 | 文本 | 计划.班次类别 | 文本（见第六节） |
| 人员.员工编号 | 文本 | 计划.参培对象 | 文本 |
| 人员.性别 | 文本（男/女） | 计划.培训地点 | 文本 |
| 人员.年龄 | 数值 | 计划.年度 | 数值 |
| 人员.干部级别 | 文本（正科级/副科级） | 计划.开始日期 | 日期 |
| 人员.职员职级 | 文本（四级职员） | 计划.结束日期 | 日期 |
| 人员.是否党支部书记 | 是否 | 计划.培训天数 | 数值 |
| 人员.是否生产分管负责人 | 是否 | 人员.任职时间 | 日期 |
| 人员.累计学时 | 数值 | 人员.任职年度 | 数值（任职时间的年份） |
| 人员.B角 | 文本 | 人员.任职年限 | 数值（到本期开始日，一位小数） |
| 人员.协理时间 | 日期 | 人员.备注 | 文本 |

> 任职时间取自人员表的 `hire_date`（导入表头写「入职时间」或「任职时间」都可以）。
> “2026年新提任” → `人员.任职年度 = 2026`。

### 指标

| 指标 | 类型 | 参数 | 含义 |
|---|---|---|---|
| 参培次数 | 数值 | `范围`：本年度 / 上年度 / 近N年（配 `年数`）/ 指定年度（配 `年度`）；`班次`：任意（默认）/ 同班次 / 同类别 / 非本班次 | 符合条件的培训记录条数；**本年度会算上本次名单里已排的班次**；近N年 = 前 N 个年度，不含本年 |
| 距上次参培年数 | 数值 | 无 | 本期开始日距最近一次历史参培的年数（一位小数），**从未参培为 99** |
| 培训期重叠 | 是否 | `区间`：`[["03-01","06-30"], ...]` | 本期起止是否与任一月日区间重叠 |
| AB角冲突 | 文本 | `时间重叠`：true（默认）/ false | 与已入选的 AB 角（双向）冲突时为对方姓名，否则为空；用 `不为空` 判断 |

### 运算符

| 类型 | 可用运算 | 值 |
|---|---|---|
| 文本 | `=` `!=` `包含` `不包含` `包含任一` `属于` `不属于` `为空` `不为空` | 文本；`包含任一/属于/不属于` 用文本数组 |
| 数值 | `=` `!=` `>` `>=` `<` `<=` `为空` `不为空` | 数字，**不加引号** |
| 是否 | `=` `!=` | 只能 `"是"` 或 `"否"` |
| 日期 | `=` `!=` `>` `>=` `<` `<=` `为空` `不为空` | `"YYYY-MM-DD"` |

`为空/不为空` 不写 `值`。数据为空时：`=` `>` 等判假，`!=` `不包含` `不属于` 判真。

## 四、标准译法（保证一致的关键，必须照用）

1. **原文有数字、日期、年份、班次名、期次，一律用原文的**。
   - 「年龄≥55岁」「满55岁」「55岁以上」→ `人员.年龄 >= 55`；「超过55岁」→ `> 55`
   - 「距法定退休年龄5年内」→ `人员.年龄 >= 55`
   - 「2026年度已参加本班次」→ `参培次数` `范围: 指定年度, 年度: 2026, 班次: 同班次`
   - 「2026年新提任」→ `人员.任职年度 = 2026`；同一计划里只说“新提任人员”时，按该计划参培对象写明的年份
   - 「3月1日至6月30日」→ `["03-01","06-30"]`
2. **原文没写数字时只能用下表默认值**（审核时用户可改）：

   | 原文说法 | 译法 |
   |---|---|
   | 学时较低 / 学时缺口 优先 | `人员.累计学时 < 100` → 25 分；`< 200` → 12 分 |
   | 近N年未参培 优先 | `距上次参培年数 >= N` → 30 分；`>= 1` → 12 分 |
   | 某类人员统一安排 / 专场 到指定期次（通用规则） | 该类人员且命中该期次 → 35 分；该类人员其它期次 → -20 分 |
   | 某类人员优先（无其它说明） | 命中 → 20 分 |
   | 某类人员靠后 / 原则上不安排（软规则） | 命中 → -20 分 |

3. **参培对象**：译成「准入」，人员范围写全（如“正科级、副科级” → `干部级别 属于 [正科级, 副科级]`；
   “含四级职员” → 另起一个或组 `职员职级 包含 四级职员`）；其中“不含……”的部分译成「剔除」分支，一类一个分支。
4. **调训规则**：按分号、顿号拆句，“不重复/不安排/不含”译成剔除，“优先安排”译成加分，
   “全覆盖”“五年全覆盖调训”这类目标性表述放进未译部分。
5. **专场**：计划里写“党支部书记专场” → 该期 `准入 人员.是否党支部书记 = 是`。
6. **身份标记用是否字段**：「党支部书记」→ `人员.是否党支部书记 = "是"`；「生产分管负责人」→ `人员.是否生产分管负责人 = "是"`。
7. **库里没有的数据**（如“班子成员”“集中轮训”“考核结果”）：能用已有字段准确表达就用（并在未译部分说明用了什么代替），
   不能的放进未译部分，由用户在审核表里决定。
8. 理由写成给人看的一句话，照原文用词。

## 六、班次类别

`计划.班次类别` 与指标里的“同类别”按班次名称归类，内置：

| 类别 | 判定（班次名称） |
|---|---|
| 新提任正职 | 同时包含「新提任」「正职」 |
| 新提任副职 | 同时包含「新提任」「副职」 |
| 县班子 | 包含「县公司领导班子」或「县班子」 |
| 进修班 | 包含「四级领导人员进修班」 |
| 其他 | 以上都不命中（「同类别」对「其他」不生效） |

需要新类别时，在草稿顶层加整张表（会替换内置表，原有四类要一并保留）：

```json
{ "班次类别": [ { "类别": "进修班", "班次名称包含全部": ["四级领导人员进修班"] }, ... ], "条款": [ ... ] }
```

## 七、审核表与防冒充（模型不得代填）

- 每行一个条件；同一条款的行连在一起，按状态排序：待审核 → 驳回 → 已确认。
- 「中文复述」把条件翻成一句话；「试算影响」是这个分支单独作用时剔除或加分的人次和样例姓名；
  「⚠」表示无人受影响或全部被剔除；「依赖本次名单」的条件（本年度参培次数、AB角冲突）试算无法预估。
- 「🔴未识别」行表示这句话没变成筛选条件：选确认即同意不执行；要执行就把它改成条件行。
- 改条件：字段/指标、运算、动作、审核结果都有下拉框；加条件就复制该条款的一行再改；删条件就删整行。
- **每个填了审核结果的条款必须填「审核人」**，并用 Excel/WPS 打开、修改、保存。

`规则 确认` 的防冒充检查：

| 检查 | 结果 |
|---|---|
| 审核单号必须是本系统签发的，且没被确认过 | 否则拒绝（不能伪造审核表、不能重复使用） |
| 审核人必填；配置了 `review.reviewers` 时必须在名单里 | 否则拒绝 |
| 文件是否经 Excel/WPS 保存、最后保存人是否变化、审核用时是否少于 `minReviewSeconds` | 记为疑点；`blockSuspicious: true` 时直接拒绝 |
| `requireTerminal: true` | 只能由用户本人在交互终端执行并输入审核人姓名，后台调用被拒绝 |

所有审核写入 `输出/规则解析/审核日志.jsonl`（逐条哈希串联）。译文库里「已确认」的条款必须在日志里有对应的确认记录、
且译文哈希一致，否则自动退回待审核——**手改译文库或审核日志都会失效并被查出**。
疑点会在每次 `名单` 时提示并写进运行记录；`node index.js 规则 审计` 查看完整审核记录。

## 八、引擎怎么执行（固定，不可配置）

1. 期次按开始日期 → 班次名称 → 期次排序，逐期处理；只评估本期**有名额单位**的人员。
2. 本期适用的条款 = 本期的参培对象、调训规则 + 全部通用规则。
3. 不依赖本次名单的准入/剔除先执行；其余人员按加分累计得分。
4. 排序：得分降序 → 累计学时升序 → 员工编号升序（无并列，结果唯一）。
5. 依次取人：单位名额满了记「顺延」；再检查依赖本次名单的准入/剔除，命中则剔除。
6. 评分 = 50 + 加分合计（限 10~100）；≥40 为高、≥15 为中，其余为低。
